Interview engine: API design

The Debrief, extracted from Out of Character into a folder the host application can copy. This page is about the seams: what each layer owns, what crosses between them, and how two very different hosts run the same code.

2 independent phases 3 seams the host implements 4 providers the host configures 5 essential guarantees 13 decisions to review Status: design for review, 2026-10-06
The short version
  1. 01Today the Debrief is one app. Sam talks to the participant; Sol, Jev and Luna think backstage; Cloudflare keeps the session alive across drops. The Conversation Map explains how that interviewer thinks. The host application needs the same interviewer inside the host app's Azure app.
  2. 02So the interviewer becomes an engine: one folder, copied as-is. The Interview phase runs the live interview and produces a transcript. The Narrative phase distils that transcript, shaped by a template, into prose. They share types and nothing else.
  3. 03The host owns the building. It implements three seams the interview cannot do without (keep a checkpoint, let model work outlive a request, keep the record) and it configures the providers: which Foundry resource, which deployments, which Langfuse project. The engine receives ready clients and never sees a key.
  4. 04Both hosts run identical engine code. Cloudflare keeps the richer wake and restore behaviour its runtime gives for free; the host app gets every essential guarantee with a Postgres row and a poll.
Analogy · the same crew, a new building

The conversation map page describes a news studio: Sam the anchor, Sol the producer with the notepad, Luna the research assistant, Jev the producer's instincts. The engine is that crew with its playbook, packed to travel.

The building they move into supplies the rest. A desk where the notepad survives a power cut (SessionStore). Permission to keep working after the segment has aired (Background). The tape library (Archive). And the phone lines to each person on the crew (Providers). Which phone company and which numbers is the building's business, never the crew's.

  • The host configures, the engine usesDeployments, keys and telemetry sinks are chosen once by the host and injected as clients. The engine calls them the same way everywhere.
  • Two phases, nothing shared but typesThe Interview phase never imports the Narrative phase, or the reverse. The host app can ship the narrative route without a TypeSafe key.
  • A seam is a purpose, not a platform featureEach seam exists because the interview needs it: a checkpoint to resume from, model work that outlives a poll, a record to write the narrative from.
  • Same crew, any buildingIdentical behaviour on Cloudflare and the host app, richer only where the runtime gives it for free.

7Cross-cutting contracts

Auth: two layers

  • Host owns identity: who the user is, who may start, rate limits, the subject.
  • Engine owns the capability: 64-hex token minted by the browser, hashed in the checkpoint, checked in the actor.
  • Engine never sees cookies. Works on a host with weak or no login.

One writer

  • At most one process writes an attempt at a time; the host supplies it.
  • Cloudflare: the runtime. The host app: the browser's socket plus a segment guard.
  • A superseded writer fails its write, closes its voice session, stops.

Cancellation

  • Every provider call takes an AbortSignal and a timeout.
  • end() aborts grading and producer work; sent with keepalive from a closing tab.
  • Narrative: cancelling the request does not cancel the run; it stays re-attachable.

Reconnection

  • Pause after 15 s WebRTC disconnected or 10 s failed polls; heartbeat every 5 s.
  • Hold 15 min, up to 5 resumes (each is a new paid voice session).
  • Auto-resume within 60 s, then the user chooses. Host does nothing.

Errors: three kinds

  • Protocol: typed errors → 400 / 401 / 404 / 410 / 429 / 503 by a default mapping.
  • Model: never reach the browser; map stays, coverage goes stale, logged with diagnostics.
  • Narrative: state, not exceptions. failure + retry while starts < 2.

Privacy

  • Leaves the box: audio and text to GPT-Live; settled text to Foundry and TypeSafe with store: false; only {kind, name, clue} to search.
  • Brief and private notes never reach the browser; a bundle check enforces it.
  • Capability never logged. Archive carries only the host's subject. This repo stays synthetic.

9Persistence and wakes

Two stores that look alike and are not, and the one timer the engine would like but does not require.

What the alarm does today, and the host app's lazy equivalent

The interview itself runs on an in-process 500 ms tick. The Cloudflare alarm is a 30 s backstop that also survives the process. It has six jobs, none of which is "run the interview".

Alarm job on CloudflareOn the host app, with no durable timer
Close orphaned paid voice sessions after a restartbrowser closes its peer first; next owner closes the recorded provider id on restore; provider's own limit bounds the rest
End a paused attempt whose browser never returns (15 min hold)hold checked on restore and resume; finalized the moment anyone touches it; costs nothing meanwhile
Finalize an interrupted attempt near its limitsame: next touch finalizes and takes Jev's final grade
Enforce idle and limit rules when polling stoppedthe tick still runs while a process holds the attempt

Rule. The alarm on Cloudflare is an optimization that makes tidy-up prompt. The host app's lack of one is a documented difference in promptness, not in correctness. No queue, cron or background worker is added to the host app.

10Who runs the session

The previous revision answered this with a lease runtime that recreated Durable Objects over Postgres. This one keeps what the runtime gives and gives the host app the smallest mechanism that is still sound.

Capability engine

This browser may drive this attempt. Minted by the browser at start, hashed in the checkpoint, checked inside the actor on every command.

Ownership host

This process may write this attempt right now. The browser never sees it. The engine meets it only as a FencedError from save.

Essential, on every host

GuaranteeWhat breaks without it
E1One writer. A superseded writer's write fails, and on that failure it stops driving the voice provider.forked transcript, two billed voice sessions
E2Serialized inside the writer. Commands, provider messages, the tick, a wake and background completions go through one mailbox.a pause racing a resume at an await
E3Successor safety. Events from a superseded voice session never act on its successor.a late session.closed pausing the new session
E4Durable before acknowledged. save returns only once durable; a resume starts from the last acknowledged transcript.recovery becomes reconstruction

No shared host type. What hosts have in common is a sentence: construct one actor per attempt you own, feed it commands, call wake if you have timers, call close when the connection or the process ends. How a host decides it owns an attempt is its own business, and the two real hosts decide very differently.

11Two hosts, one actor

Cloudflare keeps what the runtime gives. The host app scopes ownership to the browser's WebSocket and guards every write with one integer.

UPDATE debrief.interview_attempts SET segment = segment + 1, status = 'live', updated_at = now()
 WHERE id = $id RETURNING segment, checkpoint;

-- every later write by that actor: 0 rows → FencedError
UPDATE debrief.interview_attempts SET checkpoint = $cp, archive = coalesce($archive, archive), status = $status, updated_at = now()

Walkthroughs

Start

  • Browser mints id + capability, opens the socket (auth on upgrade), sends start.
  • Route inserts the row, takes segment 1, restores an actor with an empty checkpoint.
  • Actor creates the voice session, hashes the capability, saves with segment 1.

Deploy overlap

  • Old process drains: close voice, checkpoint, close socket with "resume now".
  • Browser lands on the new container, resume → segment 2.
  • A straggler's write matches zero rows, raises FencedError, dies.

Frozen process

  • Socket pings fail; client closes its peer, resumes elsewhere → segment 2.
  • Old provider id closed once by the new owner.
  • Old process wakes, writes, fenced. Participant saw "reconnecting" for ~10 s.

Crash, no drain

  • Kernel resets the socket; client resumes within seconds from the last checkpoint.
  • Tab closed instead: row stays live with stale updated_at until touched.
  • Resume button or the host application list runs the hold check and finalizes.

Acceptance criteria

The host app: two Bun processes sharing one PGlite or Postgres with a scripted provider. Cloudflare: wrangler dev.

  1. One writer. Resume on B while A is alive: A's next write raises FencedError, A closes its voice session, the row's checkpoint is B's.
  2. Serialized. Two resumes and twenty polls sent concurrently are applied one at a time; the invariant checker sees no overlap.
  3. Connection scoping. Closing the socket pauses, closes voice and checkpoints within two seconds; resumable on any instance.
  4. Drain. SIGTERM with three live attempts leaves three paused rows, three closed voice sessions, three "resume now" messages.
  5. Lazy wake jobs. With wake a no-op, a resume after the hold is refused and finalized; a stale live restore closes the recorded provider id exactly once.
  6. Transcript integrity. After a crash and resume: every passage settled before the last checkpoint, in order, nothing from the superseded segment after it.
  7. Capability. Valid token over a new socket resumes; missing or wrong is refused before any state changes.
  8. Cloudflare. Criteria 2, 6 and 7 pass unchanged; the alarm paths keep their existing tests.

13End to end

  1. Participant picks a voice. LiveConnection mints id and capability, opens the mic, sends start with an audio-only SDP.
  2. Host checks identity and rate limits, routes to the attempt. The actor hashes the capability, creates the GPT-Live session from the spec's brief, attaches the control socket, returns the SDP answer. Audio flows browser to provider directly.
  3. ready. Sam speaks. Deltas arrive on the control socket, merge into passages, settle after 1.2 s of quiet.
  4. Jev reads each settled participant turn. Sol updates the map on its own cadence (20 s to 1 min). Luna looks up a named organisation. Code ranks open threads and sends Sam a private note. Sam never sees the topics.
  5. Browser renders coverage, readings and transcript from the snapshot: polled on Cloudflare, pushed on the host app. Partial archive rows land on a timer.
  6. Train enters a tunnel. 15 s later the browser pauses. The actor closes the voice session, checkpoints, calls wake(hold): an alarm on Cloudflare, nothing on the host app. Browser heartbeats every 5 s.
  7. Signal returns. resume with a new SDP; the actor opens a new voice session with the rebuilt "conversation so far" and bumps the resume count.
  8. At ten minutes Sol's pace verdict allows a finish offer. Participant is done; Sam wraps up; ending → ended. Final grade, final archive row.
  9. Browser sends narrative to the host's route. Host reads transcript and map from the archive row, streams writeNarrative through a NarrativeRunner, stores the document on its own record. A reloaded page re-attaches or gets the stored text. The session was not involved.

14Hypotheses and things that could be simpler

  • RoleBranch is unproven. Probe whether Sol can declare a branch with a citation before fixing the type. Ship the spec without branches first.
  • Resolved: the wake belongs to SessionStore. It is per-attempt state next to the checkpoint wherever a host has it at all. Clock dropped. The wake has since become a hint the host app ignores.
  • Does GPT-Live end a session when its WebRTC transport drops? Unverified. If yes, orphans after a the host app crash cost nothing; if not, a small tasks/ sweep closes them by id. Deferred to the host app acceptance; not a blocker for the Out of Character refactor.
  • The host app could keep HTTP polling with App Service client affinity and the segment guard catching every miss. Correct but noisy; the socket makes ownership follow the connection by construction. Fallback if the second transport proves costly.
  • The host app's hold expiry is lazy. An abandoned attempt sits until touched. Nothing is billed meanwhile; a tasks/ script tidies rows if that matters.
  • ProtocolTransport could be { baseUrl, fetch }. It is a function so the host app can add headers and tests can stub it.
  • An event emitter on the session (onChange, onEnded) would suit push hosts. Not added; nothing needs it yet.
  • InterviewContext.known maps onto Sol's seed source cheaply; no caller provides it yet, but the host application almost certainly knows the project and role up front.
  • Sol's request today bypasses the AI SDK. requestSol posts to Foundry's /responses directly for prompt caching. Injecting a LanguageModel means moving that call onto the SDK with providerOptions, or giving the language provider a raw responses() escape hatch. Verify Sol's cache hit rate survives before choosing.
