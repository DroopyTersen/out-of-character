Merging the Lessons Learned questions into Sol’s closeout topics

The Lessons Learned template asks 35 scripted questions: 11 for everyone, plus five role-specific sets. This page shows where each one lands as a topic Sol works from: a criterion Jev grades against, and angles Sol can turn into its own threads. Sam never sees any of it.

35 template questions 20 base objectives (14 kept, 6 new) 1 role-only objective 5 role lenses 2 items left out

Where this plugs into the engine spec

Option C is already where the engine is headed. The API design moves topics into InterviewSpec. This proposal adds angles to each objective and reshapes role branches around them.

Already in the design

  • Topics are spec data: InterviewSpec.topics, with a criterion per objective. API design §5.1
  • Sol’s topic enum is built per spec with mapTopicIds(spec), and Jev’s coverage questions come from each criterion. Refactor plan
  • Role branches exist as a hypothesis: RoleBranch { when, add, remove }, and Sol declares activeBranches with a citation. They’re held back until a probe. Extraction plan §3.2, API design decision 6
  • InterviewContext.known already lets the host seed facts such as the role when it has them. API design §5.1, §11

What this proposal changes

  • Angles replace hint. Today hint is a generic “If it fits naturally, explore …” left over from the practice scenario. Angles are concrete unknowns Sol can turn into gap threads.
  • Branches mostly add angles. The five role lists keep circling the same few themes, so a branch sharpens shared objectives. Only one objective here exists for specific roles alone.
  • Branches never remove objectives. Vantage and set-aside already cover what a participant can’t speak to, so remove goes.

Spec types, proposed

type Objective = {
  id: string; label: string;
  criterion: string;        // Jev grades coverage against this
  angles: string[];         // new: Sol only, phrased as unknowns; replaces hint
};

type RoleBranch = {
  id: string; label: string;
  when: string;             // prose Sol judges from vantage, with a citation
  angles: Partial<Record<ObjectiveId, string[]>>;  // new
  add?: Objective[];        // rare: role-only objectives
};                          // remove?: dropped

// Sol's output keeps the design's field:
activeBranches: string[];   // each with a seed or passage citation

Sol

Criteria, angles, each branch’s when, and the active branches’ angles. Writes gap threads from them.

Jev

Criteria only, for the objectives in the active set. Angles never reach grading.

Sam

Nothing. Sam hears ranked threads, never topics, angles or lenses.

Role lens

When the role isn’t known

Nothing assumes a role. The base set is a complete interview on its own, and a lens only sharpens it.

The host knows the role

The host application passes it in InterviewContext.known. It becomes a seed fact, and Sol can turn the lens on in its first map call, citing the seed.

Nobody knows yet

The interview runs on the 20 base objectives. Sol turns a lens on once the participant says what they did, citing that passage. Until then, nothing role-specific steers the map.

More than one role

A PM who also wrote stories gets both lenses. Their angles merge, and the role-only objective joins coverage if either lens adds it.

Turning a lens on follows the same participant-fact rules applyMapUpdate already enforces for vantage. That keeps Sol from guessing a role from the project type.

Left out on purpose

  • Q9, “Which of these findings should become part of our standard delivery…”This is a judgment across many interviews. It belongs in the summary template, for example a “practices worth standardizing” section, or in a cross-interview report. It isn’t a topic Sol steers toward.
  • The 0–5 rating in Q3Dropped as a number. “How the client would judge the result, and why” survives as an angle on Success & how it landed.
  • Kickoff-checklist phrasingThe role questions ask whether something was in place at kickoff, often with the answer built in (“or still in people’s heads”). Their substance became criteria that ask what happened as a result, plus angles phrased as unknowns, never as ready questions.

Open questions for us

  1. Is 20 too many for 30 minutes?

    Each objective adds a coverage question and its evidence picks to every Jev evaluation. More gaps also compete for Sol’s two gap threads per call. Cut candidates: Why the client needed it, since the opener often covers it, or folding Shared starting picture into Deliverables & scope.

  2. Own group, or spread out?

    “How the work was set up” keeps the kickoff theme visible as one lens. Its three objectives could instead sit in the existing groups (alignment under delivered, quality and technical fit under team).

  3. Angles-first branches, or the design doc’s add: TopicGroup[]?

    I recommend angles-first. Adding topic groups per role would duplicate shared themes (non-functional requirements show up under both App and QA) and churn the active coverage set mid-interview.

  4. Which roles?

    The template has five: BA, Data engineer, App engineer, PM and QA. The extraction plan named four: developer, infrastructure, PM and BA. Infrastructure has no template questions yet.

  5. What can land now?

    The six new base objectives and their angles are a data change on interview-quality: core/interview.ts, the criteria in scenario.server.ts, and angles rendered into mapSeed, which is cached and cheap. Branches wait for the spec refactor and the probe.

  6. Can a lens turn off?

    If an early answer suggests PM and the participant later says they were the BA, does the PM lens drop, or do both stay on?
